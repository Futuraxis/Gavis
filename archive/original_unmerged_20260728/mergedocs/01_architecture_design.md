## 1. 项目愿景

### 1.1 一句话

> **任何一个策略类游戏**——无论是桌游、电子游戏、还是直播中的对局——只要你能**描述规则**或**给它截图**，Gavis 就能学会下它，并且能**实时给出对局建议**。

### 1.2 能力矩阵

| 能力 | 描述 | 状态 |
|------|------|:----:|
| 🗣️ 文本理解规则 | 输入规则说明书或代码 → 自动生成 DSL | 🟡 未实现 |
| 🎮 运行任意游戏 | 根据结构化规则 JSON 提供完整游戏环境 | 🟢 已实现 (v4.1 引擎) |
| 🧠 求解任何游戏 | MCTS / CFR / PSRO / PPO 自动选择或组合 | 🟡 部分实现 |
| 👁️ 视觉识别游戏 | 截图 / 直播画面 → 理解棋盘状态 | 🟡 部分实现 |
| 💡 实时对局建议 | 在真实游戏环境中给出下一步建议 | 🟡 部分实现 |
| 🔄 在线自学习 | 在对局中持续学习改进策略 | 🔴 未实现 |

### 1.3 用户故事

```
用户: "我想让 AI 下这个月克棋，规则是 3×3 棋盘，
       每人最多 3 个子，新子落下时最老的子消失，
       三子连珠获胜。"

                  ↓

Layer 1 Translator: LLM 将描述翻译为 rules.json
                  ↓

Layer 2 Env/Engine: 加载 rules.json → 可运行的游戏环境
                  ↓

Layer 3 Solver: MCTS/CFR/PSRO/PPO 任选训练/搜索
                  ↓

Layer 4 Interface: 
  - 用户截一张月克棋的图 → VLM 识别棋盘 → Engine 决策 → 给出建议
  - 用户反馈胜负结果 → Solver 在线更新策略
```

## 3. Layer 1: Translator — LLM 翻译层

### 3.1 定位

图中缺失的一环。将人类可读的策略游戏规则**翻译为机器可执行的 `rules.json`**。

### 3.2 输入/输出

| 输入类型 | 示例 | 难度 |
|---------|------|:----:|
| 自然语言规则文本 | "围棋是 19×19 棋盘，黑白交替落子，围地多者胜" | 高 |
| 开源游戏代码 | GitHub 上的月克棋 Python 实现 | 中 |
| 规则 PDF/图片 | 规则书的扫描件 | 极高 |
| 结构化规则模板 | 用户填写的规则表单 | 低 |

### 3.3 关键技术问题

1. **规则完整性验证**：LLM 输出的 rules.json 是否能驱动完整的游戏？需要 Engine 回环验证
2. **歧义消解**：自然语言中"吃掉对方的子"在 Engine 中可能对应多种 effect 组合
3. **状态表示设计**：不同的游戏可能需要不同的 state 结构，Engine 的抽象是否足够通用
4. **错误恢复**：LLM 输出格式错误 → 自动修复 → 重试

### 3.4 当前状态

**未实现。** 这是项目后续最关键的扩展方向。

## 4. Layer 2: Env/Engine — 游戏引擎层

### 4.1 定位

项目的核心基础设施。接收 `rules.json`，提供完整的游戏运行环境。

### 4.2 当前实现

位置：`gavis/core/`

```
GameEngine
  ├── create_initial_state()         → 根据 rules.json 初始化状态
  ├── get_node_type(state)           → player / chance / terminal
  ├── get_legal_actions(state)      → 根据 action template 展开合法动作
  ├── apply_action(state, action)    → 执行 effect chain
  ├── get_chance_outcomes(state)     → 展开随机节点的可能结果
  ├── apply_chance(state, outcome)   → 执行 chance effect
  ├── is_terminal(state)             → 检查终止条件
  ├── get_utility(state, player)     → 返回玩家收益
  ├── get_observation(state, player) → 返回观测 (用于 RL 求解器)
  └── get_info_set_key(state, player)→ 返回 info set key (用于 CFR)
```

### 4.3 支持的规则元素

```
rules.json v4.1:
├── constants      — 游戏常量 (棋盘大小、概率等)
├── queries        — 状态查询 (空格子等)
├── actions        — 动作模板 (带参数域、合法性、effect 引用)
├── effects        — 效果指令 (set / inc / branch / forEach / ...)
├── chance         — 随机节点 (概率分布 + 效果映射)
├── phases         — 游戏阶段 (回合流程)
├── terminal       — 终止条件
├── utility        — 收益函数
└── functions      — 自定义函数 (如 check_five_in_row)
```

### 4.4 当前局限

| 局限 | 描述 | 优先级 |
|------|------|:------:|
| 只有一种游戏实装 | stochastic_gomoku 是唯一被 rules.json 定义的游戏 | P0 |
| 月亮棋未用引擎 | 成员 A/B 各自独立实现了月亮棋，未用 GameEngine | P0 |
| pieceOrder 不支持 | 月亮棋"先落先消"需要队列语义，Engine 不原生支持 | P1 |
| 性能未优化 | 大棋盘 (19×19) 的 action 展开可能很慢 | P2 |

## 5. Layer 3: Solver — 求解器层

### 5.1 定位

提供多种求解算法，让 Engine 中的游戏可以被 AI 学会或搜索出最佳策略。

### 5.2 当前实现

| 求解器 | 文件 | 算法 | 适用场景 |
|--------|------|------|---------|
| MCTS | `gavis/solvers/mcts.py` | 蒙特卡洛树搜索 (带 chance 节点) | 在线搜索，无需预训练 |
| CFR | `gavis/solvers/cfr.py` | External Sampling MC-CFR | 离线均衡计算 (小游戏) |
| PPO | `未命名文件夹/algorithms/ppo_agent.py` | PPO-clip + GAE | 深度 RL，有泛化能力 |
| PSRO | `moon_chess_ai/PSRO/train.py` | 策略空间响应 Oracle | 策略多样性 + 纳什均衡 |

### 5.3 理想中的 Auto-Selector

**远期目标：** 根据游戏特征自动选择最佳求解器组合：

```python
auto_select(game_features):
  - 状态空间 ≤ 10⁶ → PSRO (表格方法，精确均衡)
  - 有随机节点 → MCTS (自然处理 chance)
  - 状态空间大 → PPO (神经网络泛化)
  - 需要均衡解 → CFR (理论保证)
  - 有视觉输入 → PPO + Binding (端到端)
```

### 5.4 关键缺口

| 缺口 | 影响 |
|------|------|
| 各求解器互不兼容，不能比较 | 无法自动选择最优算法 |
| PSRO 缺依赖 (Agent 类) | 代码不可运行 |
| PPO 训练不足 (20 episodes) | 策略质量不可用 |
| 无统一求解器接口 | Auto-Selector 无法实现 |

## 6. Layer 4: Interface — 交互界面层

### 6.1 定位

连接真实世界与 Engine。一方面从截图/直播中**识别游戏状态**，另一方面向用户**展示对局建议**，同时**收集反馈用于在线学习**。

### 6.2 当前实现

位置：`未命名文件夹/binding/`

```
Interface Layer
├── ImageBinding           — OpenCV 模板匹配，拆分棋盘格子
│   └── CellClassifier     — 启发式分类器 (X / O / 空)
│
├── VisionLLMBinding       — 视觉大模型 (Qwen-VL) 整图识别
│   └── VisionModelClient  — 模型 API 适配器
│
├── MockBinding            — 测试用 mock
│
├── StateTracker           — 跨帧追踪，推断 pieceOrder
│   关键作用: 单帧截图无法知道棋子顺序，需要多帧上下文
│
├── Observation (pydantic) — 统一输出格式
│
└── app_server.py + HTML   — Web 演示界面
```

### 6.3 理想形态

```
┌─────────────────────────────────────────────────┐
│              真实世界输入                         │
│  桌面截图 🖥️  │  棋牌 App 📱  │  直播画面 📺   │
└──────────────┬──────────────────┬───────────────┘
               │                  │
┌──────────────▼──────────────────▼───────────────┐
│            VLM 多模态识别                        │
│  - 定位棋盘 (不依赖裁剪)                          │
│  - 识别棋子类别和位置                             │
│  - 处理视频流 → 增量更新                         │
│  - 置信度不够时主动请求用户确认                    │
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│              StateTracker                        │
│  - 跨帧消除歧义 (顺序推断)                       │
│  - 检测用户落子 → 自动触发 Engine 决策           │
│  - 检测对局异常 → 请求用户重新截图                │
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│              GameState → Solver                  │
│  - 当前状态送入所选求解器                         │
│  - 求解器返回建议动作                             │
│  - Interface 渲染建议 (高亮 / 箭头 / 文字)        │
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│              在线自学习                           │
│  - 用户按建议落子后 → 获取最终结果 → 反馈给 Solver│
│  - PPO: 添加到 experience replay                 │
│  - PSRO: 添加到策略池评估                         │
│  - CFR: 继续迭代                                 │
└─────────────────────────────────────────────────┘
```

### 6.4 当前缺口

| 缺口 | 影响 |
|------|------|
| ImageBinding 只支持 3×3 裁剪图 | 无法处理任意棋盘 |
| VisionLLMBinding 依赖外部 API | 延迟和成本问题 |
| StateTracker 未对接 Solver | 识别后没有 AI 建议 |
| 无在线学习回路 | 识别的结果没有被用来改善策略 |
| 无用户反馈机制 | 无法从错误中恢复 |

## 7. 跨层数据流

### 7.1 完整流程 (从规则到对局建议)

```
用户描述规则 "月克棋是..."
        │
        ▼
┌──────────────────┐
│  Layer 1          │  Translator (LLM)
│  "月克棋" → rules.json  │
└────────┬─────────┘
         │ rules.json
         ▼
┌──────────────────┐
│  Layer 2          │  Env/Engine (GameEngine)
│  加载 rules.json  │
│  提供游戏环境     │
└────────┬─────────┘
         │ SolverAdapter 接口
         ▼
┌──────────────────┐
│  Layer 3          │  Solver (PPO / MCTS / ...)
│  训练/搜索策略   │
│  返回动作建议    │
└────────┬─────────┘
         │ 动作
         ▼
┌──────────────────┐
│  Layer 4          │  Interface (Binding)
│  用户截当前棋盘图 │
│  VLM 识别 → Engine调用→ 显示建议 │
│  用户反馈结果 → Solver在线学习│
└──────────────────┘
```

### 7.2 核心数据格式

**层与层之间的唯一契约：**

```
Layer 1 → Layer 2: rules.json  (声明式规则)
Layer 2 → Layer 3: SolverAdapter (Python Protocol)
Layer 3 → Layer 4: ActionInstance (决策结果)
Layer 4 → Layer 2: GameState dict (识别出的状态)
Layer 4 → Layer 3: 胜负反馈 (在线学习信号)
```

## 8. 在线自学习闭环

### 8.1 闭环流程

这是项目最核心的创新点——**Solver 在真实对局中持续学习**：

```
                 ┌─────────────────────┐
                 │  用户真实对局         │
                 │  (截图 + 用户落子)    │
                 └────────┬───────────┘
                          │
              ┌───────────▼───────────┐
              │  Interface Layer       │
              │  VLM 识别 → GameState  │
              └───────────┬───────────┘
                          │
              ┌───────────▼───────────┐
              │  Solver 给出建议动作   │
              │  (MCTS 搜索 / PPO 前向)│
              └───────────┬───────────┘
                          │
              ┌───────────▼───────────┐
              │ 用户选择:              │
              │  a) 按建议落子         │
              │  b) 选不同的位置       │
              └───────────┬───────────┘
                          │
              ┌───────────▼───────────┐
              │  对局结束             │
              │  输/赢 → 学习信号     │
              └───────────┬───────────┘
                          │
              ┌───────────▼───────────┐
              │  Solver 在线更新       │
              │  PPO: replay buffer   │
              │  CFR: 额外迭代        │
              │  PSRO: 评估新策略     │
              └────────────────────────┘
```

### 8.2 技术挑战

| 挑战 | 说明 |
|------|------|
| **延迟** | 在线学习不能阻塞用户，更新需在后台异步执行 |
| **非完整轨迹** | 用户可能从中局开始截图，Solver 需要处理部分可观测性 |
| **用户噪声** | 用户可能不按规则落子，需要 engine 验证合法性 |
| **策略漂移** | 在线更新可能导致策略质量波动，需要回滚机制 |
| **数据效率** | 真实对局数据量小，需要样本高效的学习算法 |

### 8.3 当前状态

**未实现。** 这是项目最终的进化目标，当前各层还没有任何一层支持在线闭环。
