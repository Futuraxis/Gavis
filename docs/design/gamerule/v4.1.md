下面是一份可直接作为项目基础规范使用的 \*\*通用游戏规则语言设计文档 v4.1\*\*。它延续你前面的 v4.0 图模型，但把 `rules` 从“DSL 字符串容器”升级为\*\*声明式、结构化、可编译、可动态展开动作空间\*\*的规则语言。核心目标是：\*\*不枚举完整动作空间、不枚举信息集、不枚举博弈树，而是用 JSON/DSL 描述生成规则\*\*。

\# 通用游戏规则语言设计文档 v4.1



\## 1. 设计目标



本语言用于描述大多数回合制、棋类、卡牌、桌游、战棋、解谜类游戏的规则系统。



它不是某一个游戏的专用脚本语言，而是一套基于 JSON AST 的声明式规则语言，用于定义：



\- 游戏状态如何组织；

\- 玩家在当前状态下有哪些合法动作；

\- 动作参数如何动态生成；

\- 动作如何改变状态；

\- 随机事件如何产生；

\- 玩家可见信息如何投影；

\- 游戏何时终局；

\- 终局收益如何计算；

\- 日志与回放如何规范化；

\- AI 求解器如何基于规则生成动作、观察和收益。



核心原则是：



> \*\*规则 JSON 存动作模板，不存动作实例；存观察规则，不存信息集；存随机分布，不存完整随机历史。\*\*

\### 8.3 动作生成语义



给定一个 `ActionTemplate`，运行时按以下顺序生成动作：



1\. 检查当前 `env.phase` 是否在 `phases` 中；

2\. 计算 `actor`；

3\. 对每个 `params` 计算候选域；

4\. 对候选参数应用 `filter`；

5\. 对多个参数做笛卡尔积组合；

6\. 对每个参数组合计算 `legal`；

7\. 通过者生成 `ActionInstance`；

8\. 为每个动作实例生成 `canonicalKey`。

\## 18. 运行时执行语义



\### 18.1 动作展开

expandActions(state, rules):

&#x20; for template in rules.actions:

&#x20;   if phase mismatch: continue

&#x20;   actor = eval(template.actor)

&#x20;   domains = eval param domains

&#x20;   combinations = cartesian(domains)

\## 20. 安全性与确定性约束



\### 20.1 禁止非确定性表达式



规则表达式中不得直接调用系统时间、网络请求、随机数 API。



随机必须通过：



```typescript

ChanceTemplate

```



或受控的：



```typescript

ShuffleOp

DrawOp

```



\### 20.2 外部函数限制



外部函数分为：



| 类型 | 是否允许改状态 | 是否可用于求解 |

|---|---:|---:|

| `pure: true` | 否 | 可 |

| `pure: false` | 可选 | 不推荐 |

| `solverSafe: true` | 否 | 可 |

| `solverSafe: false` | 不限 | 不可用于 CFR |



\### 20.3 执行顺序确定



以下结构必须排序稳定：



\- `actions` 按定义顺序；

\- 参数候选按 canonical ID 排序；

\- `triggers` 按 priority，再按定义顺序；

\- `utility` 按定义顺序合成；

\- `visibility` 按 priority，再按定义顺序。

\## 21. 规范化与哈希



为了日志、回放、求解器复用，必须定义 canonicalization。



\### 21.1 Canonical JSON



要求：



\- 对象 key 按字典序排序；

\- 数组保持语义顺序；

\- 忽略运行时无关字段；

\- `undefined` 不允许出现；

\- 浮点数格式统一；

\- 节点 ID 使用稳定字符串。



\### 21.2 Action Key



动作实例必须有：



```typescript

canonicalKey: string;

```



推荐格式：



```text

templateId:param1=value1:param2=value2

```



\### 21.3 Abstract Key



用于 AI 抽象：



```typescript

abstractKey?: string;

```



例如：



```text

真实动作：use\_card:card\_007->p2

抽象动作：use\_card:slash->enemy

```

\## 22. 错误处理



\### 22.1 编译期错误



| 错误 | 示例 |

|---|---|

| 引用不存在 | `effectRef` 指向不存在效果 |

| 函数未声明 | `call` 调用未知函数 |

| 类型不匹配 | number 与 node 比较 |

| 参数未绑定 | 使用 `$target` 但未定义 |

| 路径非法 | `state.foo.bar` 不存在 |

| 概率非法 | 概率和不为 1 |



\### 22.2 运行期错误



| 错误 | 处理 |

|---|---|

| 参数候选为空 | 不生成动作 |

| legal 为 false | 动作非法 |

| 节点不存在 | 拒绝动作 |

| 效果执行失败 | 回滚该动作 |

| 外部函数异常 | 标记规则错误 |

| 概率归一化失败 | 拒绝 chance 展开 |

\## 26. 总结



这套 v4.1 语言的核心设计是：



```text

StateGraph 存当前世界

RulesLibrary 存世界运行规律

ActionTemplate 动态生成动作

EffectDef 描述状态变更

VisibilityRule 生成玩家观察

ChanceTemplate 描述随机节点

TerminalRule 判断结束

UtilityRule 计算收益

```



它避免了显式枚举动作空间的 JSON 爆炸，同时又为 CFR / MCTS / Minimax / 普通规则引擎提供了足够清晰的接口。



最关键的一句话是：



> \*\*JSON 里不存博弈树，而是存“如何生成博弈树”的规则。\*\*
